# یادداشت برای ادامه‌ی کار (Claude Code)

این فایل را قبل از پیاده‌سازی فیچرها بخوان. مرحله ۰ (ساختاردهی) کامل و تست‌شده است.

## قواعد معماری که نباید شکسته شوند

1. **لایه‌بندی import:** هر ماژول فقط از ماژول‌های «قبل از خودش» import می‌کند (ترتیب در `docs/module_order.txt`). import حلقوی نداریم؛ نگهش دار.
2. **هندلرها:** ماژول‌های `app/handlers/` هرگز از یک ماژول هندلر *بعدی* import نکنند. اگر import کنند، ترتیب ثبت هندلرها عوض می‌شود. توابع مشترک را در `app/screens.py`، `app/flows.py` یا ماژول‌های منطق بگذار.
3. **ترتیب ثبت:** ترتیب در `app/handlers/__init__.py` تعیین می‌شود. هندلر پیام جدید را **قبل از `fallback`** اضافه کن. هندلر `fallback` همه پیام‌های پی‌وی بدون state را می‌گیرد. تست `tests/test_structure.py` باید سبز بماند.
4. **داده‌ی سراسری:** فقط در `app/state.py`. متغیری که دوباره مقداردهی می‌شود (نه dict/list) را با `from app import state as app_state` و `app_state.X` بخوان و بنویس. هرگز `from app.state import X` برای این‌ها استفاده نکن.
5. **ذخیره‌سازی:** هر داده‌ی جدید باید به `snapshot()` و `apply_data()` در `app/storage.py` اضافه شود. بکاپ‌های قدیمی بدون آن کلید هم باید سالم لود شوند.
   **توجه:** `apply_data` فقط کلیدهای مشخصی از SETTINGS را بازیابی می‌کند (لیست صریح دارد). کلید جدید SETTINGS را به آن لیست اضافه کن، وگرنه با ری‌استارت پاک می‌شود.
6. **تست:** برای هر فیچر با `tests/fakebot.py` یک تست مسیر کامل بنویس (آپدیت جعلی → چک پیام‌های ارسالی).

## قانون دید بازیکن (fog of war)

- پلیر هرگز آمار نیرو یا دارایی شهر دیگر را نمی‌بیند. **استثنا:** لیدر جناح، که الان هم شیت شهرهای جناح خودش را می‌بیند.
- پست‌های کانال فقط مبدأ، مقصد، هدف، نوع و زمان رسیدن را دارند. آمار لشکر، محموله‌ی تجارت و آمار کمین فقط در گزارش ادمین است. وقایع‌نامه و هر چیز عمومی فقط از همین اطلاعات عمومی ساخته شود.
- **متن غلط در کد:** پیام هشدار تهدید (`app/threats.py`) می‌گوید «آمار مهاجم در کانال اصلی اعلام شده است». این درست نیست، چون آمار عمومی نمی‌شود. متن را اصلاح کن.

## xAI (کلید رایگان، سهمیه کم)

- هیچ کار خودکار یا زمان‌بندی‌شده نباید xAI صدا بزند.
- تصویر با Pillow محلی ساخته شود، نه API.
- وقایع‌نامه پیش‌فرض با قالب محلی نوشته شود. «بازنویسی با گروک» فقط با دکمه باشد، نتیجه‌اش کش شود و سقف روزانه داشته باشد.

## باگ‌های پیداشده (هنوز رفع نشده)

1. **باف ساختمان‌های سکه‌ای:** در `app/economy/up.py` → `run_weekly_up_for_city`، بافی با هدف «خزانه/بندر/تجارتخانه» درصدش را از **جمع کل سکه** می‌گیرد (`base = deltas["سکه"]`). باید از بازدهی همان ساختمان گرفته شود (`_yield_of(target)`).
2. **دکمه‌ی «🔙 پنل ادمین»:** این دکمه در منوهای آپ (`callback_data="adm_back"`) هیچ هندلری ندارد. یا به `back_to_admin` وصلش کن یا callback را عوض کن.
3. **دابل‌کلیک ارتقا:** دکمه‌ی ارتقا (`upg:do:` در `handlers/economy.py`) بدون تایید و بدون قفل اجرا می‌شود. دابل‌کلیک = دوبار کسر هزینه.
4. **دابل‌کلیک کاروان:** در تایید کاروان بازیکن (`trade_ok` در `handlers/trade.py`)، بین چک وضعیت و `status="approved"` یک `await post_to_channel` هست. دابل‌کلیک = دو پست و دوبار کسر ظرفیت. قبل از await وضعیت را `processing` کن.
5. **ورود مالک:** مالک (`ADMIN_ID`) با `/start` در پی‌وی، اگر رکوردی نداشته باشد، کد ورود می‌خواهد. بهتر است مستقیم پنل باز شود.
6. **متن ظرفیت لیدر:** هشدار ظرفیت لیدر در `set_leader_side` می‌گوید «۳/۳»، ولی سقف واقعی ۵ است.
7. **دکمه‌ی ارتقا:** متن صفحه‌ی ارتقا می‌گوید «پس از تایید اعمال می‌شود»، ولی تاییدی وجود ندارد.

**پیشنهاد اجرا:**
- فعال‌سازی با کلید `castle_buffs`، پیش‌فرض **خاموش**. ممکن است ادمین‌ها الان این باف‌ها را دستی اعمال کنند و نباید دوبار حساب شوند.
- قبل از روشن شدن، پیش‌نمایش نشان داده شود.
- با خاموش کردن، باف‌های `source="castle"` حذف شوند.

**باف‌های هزینه:** از مکانیزم موجود استفاده کن: `CITY_BUFFS` با `effect="cost"` و `upgrade_cost_modifier`. برای Leeds باید مکانیزم «فقط سکه» اضافه شود.

## قوانین زمانی (از `_RULES_DIGEST` در `app/economy/rules.py`)

- بازی شنبه تا چهارشنبه است.
- ارتقا سه‌شنبه و چهارشنبه.
- تجارت با بازیکن شنبه و یکشنبه، تجار دوشنبه.
- آپ بعد از استاپ چهارشنبه.
- python weekday: دوشنبه=0 … یکشنبه=6.

ربات الان هیچ‌کدام را اجرا نمی‌کند. پیشنهاد: کلید `rules_calendar` با پیش‌فرض خاموش.

## فایل‌های docs/wip (پیش‌نویس، وصل نشده، تست نشده)

- `features.py`: کلیدهای روشن/خاموش فیچرها در `SETTINGS["features"]`، به‌علاوه‌ی تنظیمات تکمیلی.
- `permissions.py`: این‌ها را دارد:
  - `roles_of` و جدول `PERMS` و `can()`
  - `assistant_allowed` برای اختیارات کمکی
  - `AclMiddleware` که پیشوندهای callback ادمینی را مرکزی می‌بندد
- `audit.py`: این‌ها را دارد:
  - لاگ ممیزی با `contextvar` برای تشخیص انجام‌دهنده (نیاز به یک outer middleware روی `dp.update` دارد که `CURRENT_ACTOR` را ست کند)
  - دکوراتور `@audited` برای توابع تغییر دارایی
  - برگشت (undo) با چک fingerprint

می‌توانی این‌ها را مبنا قرار بدهی. **قبل از استفاده:**
- آن‌ها را به `app/` منتقل کن.
- داده‌هایشان را به `state.py` و `storage.py` اضافه کن.
- برایشان تست بنویس.
